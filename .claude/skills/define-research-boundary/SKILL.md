# Define Research Boundary

> 研究做到一定阶段:大方向摸清了(research 跑过,处境/硬骨头/路径出来了),但还没到写详细系分细看代码的程度。这时候容易**发散**(啥都想查)或**漏关键投入点**(该精研的没研)。本 skill 定"研究边界":还没透的几个方向、每个大概往哪查、大概能解什么,让下一步精研有边界不乱跑。

**产物是给用户看的**——用户读了这份边界清单,才知道"下一步该精研哪几块、每块往哪查"。所以可读、清楚是硬要求:不是 AI 内部 todo,是指导用户下一步研究方向的文档。

## 何时用

- research 摸清了大方向(处境/硬骨头/路径已出),但还没深入代码
- 想"我现在该专注把哪几块搞透",不想发散也不想漏
- **不是写详细系分时用**——那是要验到文件行的细活,本 skill 只给大概率方向

不该用:
- 还没摸处境(先去 research)
- 已经在写详细系分(去看代码,不用定边界)

## 输入

- research 的思维链 + 决策链(摸到啥、推出啥硬骨头、排了啥路径、做了啥决策)
- 已知资源(本地仓库、文档、可问的人)
- 可选:自己 web 查的补充方案/业界做法

## 防过拟合(写/用都要守)

- **不给精确到文件行的指引**——那是详细系分的事,本 skill 到"大概率方向"(看哪个仓库/哪块能力/哪类参照)就够
- **不套固定方向清单**——每个项目没透的方向不同,自己从 research 推理得出,别抄别的项目的方向
- **不趁机又把活甩给老板**——能查清的方向归"待研究"(我去查),不归"待决策"(老板定)。见 write-design-by-priorities 的"待研究vs待决策"

## 产出:研究边界清单

几个还没透的方向,每个写清楚三样:

1. **是什么没透** —— 具体哪个点还没搞清楚(不是泛泛"GE 能力",是"某能力工程量多大""某俩包什么关系"这种具体的)
2. **大概往哪查** —— 大概率看哪些资源能解(本地哪个仓库/哪块能力/哪个参照项目/问谁/web 查什么)。**给方向,不到文件行**
3. **大概能解什么** —— 查清楚了能回答什么问题、对方案意味着什么(解了能定某个取舍/某条路径/某处协作边界)

收口一句话(关键):**这些方向理论上够把需求解了,剩下的就是细看代码借鉴参照、解决具体卡点。** 这一收口是本 skill 的核心价值——确认"研究范围闭合了",不用再发散找别的。

## 产出形态示例(抽象示意,别照抄)

某个"格式 A 转 B"需求,研究边界可能是:

| 没透的方向 | 往哪查 | 能解什么 |
|---|---|---|
| 目标格式加新类型工程量多大 | 看目标格式那个包的现有类型怎么加的、谁维护 | 定要不要加(待决策前先查清) |
| 俩相关仓库是什么关系 | 看 git log/问维护人 | 定协作是上下游复用还是并列 |
| 某卡点能力参照项目解过没 | 看参照项目那块怎么处理的 | 照搬/避坑,定卡点解法 |

收口:这三个方向理论上够(知道工程量、知道协作、知道卡点解法),剩下的就是细看代码借鉴 + 解卡点。

**这是示意,你项目的方向自己从 research 推。**

## 判据:边界定对了吗

- [ ] 没透的方向都列全了?(没漏关键投入点)
- [ ] 每个方向给了大概往哪查?(不是空指路"去看代码")
- [ ] 能收口"这些理论上够解"?(如果收不了口 = 还漏方向,继续找)
- [ ] 没把待研究伪装成待决策甩出去?(能查清的是待研究)
- [ ] **用户读这份清单能直接开干?**(读完知道下一步精研哪、往哪查,不用再猜——这是"给用户看"的硬要求,不是内部 todo)

## 一句话

> 研究到一半定边界:还没透的几个方向、每个往哪查、能解什么,最后收一句"这些理论够,剩下细看代码"。让精研有界不发散、不漏关键投入点,也不该甩给老板的别甩。

# Research Pipeline(编排器)

> 自己不干活,只告诉 AI"现在该用哪个子 skill、什么条件触发、何时回头、文档写哪"。把现有 skill 串成"研究一个大需求"的完整流程。AI 调它一次,照它的流向调子 skill。
> **不带固定步骤数**——给拓扑+触发条件+回头条件,小需求/已想清的不进入编排。

## 何时用编排器 vs 直接调子 skill

- **用编排器**:模糊大需求、不知从哪入手、要跑完整研究链(摸处境→定边界→精研→写文档)
- **直接调子 skill**(别走编排器):
  - 已知现在要写浅显方案 → `write-design-by-priorities` / `write-doc-clean`
  - 已知现在要写细致系分 → `write-detailed-spec`(它自己硬依赖 deep-read)
  - 已知现在要定点啥 → 单个动作别套

编排器别滥用:小需求/已想清的,要哪个子 skill 直接调,别走编排器走过场。

## 整套拓扑(有回环,不是固定流水线)

```
模糊大需求
   │
   ▼
[research-before-design]  摸处境/抓硬骨头/排路径/产重要推理
   │ 验:处境摸清?硬骨头抓到?路径排好?重要推理产出?
   ├─ 没 → 继续 research(别装懂往下走)
   └─ 有 → 分叉,看需求产出要哪种文档:
              │
              ├─【要浅显方案(给人看懂怎么做)】→  [write-design-by-priorities]
              │    (硬依赖 research 重要推理,转译成浅显叙事,不写代码级)
              │    │ 验:每节读者能接着看到 why?没堆结论盒子/没 AI 自省?
              │    └─ 有问题 → 回 research 补
              │    ✅ 产出=浅显方案文档 → 按下方"文档落点准则"落到语雀/本地(同样要写不要只装脑子里)
              │
              └─【要细致系分(给实施用,代码级)】→ 继续:
                  │
                  ▼
               [define-research-boundary]  定边界:没透的方向+往哪查+能解什么+收口
                  │ 验:边界闭合(能收口"这些理论够,剩细看代码")?
                  ├─ 没(还漏) → 补边界;漏的是硬骨头/处境 → 回 research 抓
                  └─ 有 → 产边界文档(粗粒度指路,给用户看下一步精研哪)
                          ↓
                  [deep-read-by-boundary]  按 boundary 逐块精研(research 同思维落点到细)
                     │ 验:每块透了(能据此写代码级)?有前提被推翻?
                     ├─ 前提推翻 → 回 research 重摸那块
                     ├─ 撞子边界 → define-research-boundary 给那块定子边界,再 deep-read 一轮
                     └─ 都透 → 产精研结论
                             ↓
                     [write-detailed-spec]  接精研结论写细致系分(interface/JSON/示例/实现流程)
                        │ 验:每节能落代码级?风格像人写反 AI 腔?
                        ├─ 落不下 → 回 deep-read 再研那块(别标 TODO 硬编)
                        └─ 能落 → 产出=细致系分文档
                             ↓
                ┌────────────────────────────────────────────────────┐
                │ 两条产物线共用这一环(浅显方案 / 细致系分 都必走)      │
                └────────────────────────────────────────────────────┘
                             ↓
                  [adversarial-self-check]  产出对抗自检(承接 grill 的"职员级怀疑、不让 ship"精神)
                     │ 验:用 staff engineer 怀疑态通读刚写的文档,逐项查:
                     │   - 自相矛盾:前后段/示例与正文/签名与伪码/文档与真身类型
                     │   - 技术断言有没源码撑(怀疑式核,像"position 语义"这种易脑补的尤甚)
                     │   - 数字/示例是否凭空(ratio 换算、具体值对得上算法么)
                     │   - 接口/类型与真身(data.ts/schema)对得上么
                     ├─ 破绽是"没核透"(断言脑补) → 回 deep-read/research 核证再修
                     ├─ 破绽是"写错"(笔误/矛盾) → 改完重检
                     ├─ NEEDS WORK/BLOCK → 不放过,改完重走这环
                     └─ SHIP IT → ✅ 按下方"文档落点准则"落到语雀/本地 → 实施代码

                     ⚠️ 修文档时**不留订正痕**(不作废标注、不自省段),改完读起来像初始结论;实在要保留演进可另起审计文件放本地 `.claude/plans/`(语雀文档保持干净初版态)。
```

> **注意**:这一环不是调 `/grill` 命令——grill 是 git diff 代码审查形态,不适用文档通读。承接的是它的对抗精神(`SHIP IT/NEEDS WORK/BLOCK` + 职员怀疑 + 不让 ship),针对"研究产出文档"的自检清单见上面验点。

> **所有产出(浅显方案/边界指路文档/细致系分)都要落到文档**,按"文档落点准则"——别只装脑子里。研究文档也得记下来(供下一步精研和审计)。
```

## 回头条件汇总(精细需求不只一轮,该回头不硬撑)

- **research 时**:deep-read/写时发现前提假设被推翻、硬骨头漏或抓错、新相关物没纳入 → 回 research 重摸那块
- **boundary 时**:边界收不了口 = 还漏方向;漏的是硬骨头 → 回 research;是新子方向 → 用 boundary 给子边界
- **deep-read 时**:前提推翻回 research;撞更深没透的子边界→定子边界再研;每块都要标透没透,没透别假装
- **write 时**:落不下代码级回 deep-read;浅显方案没 why 回 research 补
- **adversarial-self-check 时**:破绽是脑补断言(没核透)→ 回 deep-read/research 核证,别凭印象改;破绽是笔误/矛盾 → 改;**改不留订正痕**(语雀文档保持干净初版态,演进存本地审计文件);NEEDS WORK/BLOCK 不放 ship,改完重检

**原则:没透就回头,不硬往下走/不硬编/不标 TODO 蒙混;写完不自检就落文档等于把脑补固化成事实,adversarial-self-check 是最后一道闸。**

## 文档落点准则(写文档时按这个)

研究/写产物要落到文档,按这准则放:

**用语雀 CLI 写到个人默认知识库:**
- 命令:`yuque`(之前已装)。主要用 `yuque create doc` / `yuque update doc` / `yuque show toc-format` / `yuque update toc-format`
- 目标:个人默认知识库(类似 `guoshiquan.gsq/kb` 那种 namespace)。CLI 通就用 CLI 写到那

**放哪:看现状定,别堆叠旧文档:**
- 先 `yuque show toc-format` 看当前知识库 TOC,知道有哪些文档、挂哪
- 看当前目录(可能已有 `.claude/plans/` 之类)是否有同主题旧文档
- 新文档:`yuque create doc` 建后,用 `yuque update toc-format` 挂到合适的 TOC 位置
- **TOC 更新手顺坑**(踩过):用 `title + slug + doc_id` 三元组**全量**写,不能用简化格式,否则会清空整个 TOC

**CLI 不通降级本地:**
- CLI 报错/没装/鉴权失败 → 写到本地 `.claude/plans/<主题>.md`,告诉用户后续手动上传

**别堆叠旧尝试:**
- 反复改的文档,该新建就新建(用 `create`),别在旧 doc 上反复 `update` 把旧底子带进新内容
- 要删的旧文档:CLI 不支持删 doc,只能 `update toc-format` 把它从 TOC 移除(脱离目录树),文档本体要用户网页删

判据:文档放好了吗?CLI 通了写知识库、不通写本地;TOC 没清空、没堆叠旧文档、命名不冲突?

## 防过拟合 + 防滥用

- **别把这套拓扑当固定步骤数硬走**——是"拓扑+条件",按实际需求走/回头/短路,几步都行
- **别滥用**:小需求直接调子 skill,别走编排器走过场(研究阶段陌生大需求才用)
- **别让编排器代替子 skill 干活**——编排器只说"调哪个",不替子 skill 做内容
- **别因为流程长就硬走全套**——很多需求某个 skill 走完就够,不用走完整链(比如只要浅显方案,research 出推理直接 write-design-by-priorities,不进 boundary/deep-read)

## 判据:编排跑对了吗

- [ ] 仅在"模糊大需求、不知从哪入手"时进编排器?没对小需求滥用?
- [ ] 走对拓扑?每步触发条件验过了(摸清没/边界闭合没/透没/落得下没)?
- [ ] 该回头时回头了?没硬往下走/硬编/标 TODO 蒙混?
- [ ] 写完文档**走了 adversarial-self-check**?通读查了自相矛盾/断言有没源码撑/数字凭空/类型对真身?SHIP IT 才落文档?(没自检就落文档=把脑补固化成事实)
- [ ] 自检改文档**不留订正痕**(语雀干净初版态、演进存本地)?
- [ ] 文档落到该落的位置?CLI 通写知识库+TOC 三元组全量、不通降本地?
- [ ] 没堆叠旧文档、没在旧 doc 上反复 update 带旧底子?

## 一句话

> 串现有 skill 成"研究大需求"完整链:research→boundary→deep-read→write→**adversarial-self-check(承接 grill 精神,产出落地前职员级怀疑自检,防脑补断言/自相矛盾固化进文档)**,带触发条件和回环(没透就回头不硬撑),加文档落点准则(语雀 CLI 写默认知识库/看现状放/不通降本地/不堆叠旧)。小需求直接调子 skill 别走编排器。

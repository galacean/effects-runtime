# Write Detailed Spec

> 精研透了(deep-read-by-boundary 出结论了),写代码级细致系分——到 interface、JSON 数据设计、示例、渲染/实现流程那级。这不是浅显方案(那是 write-design-by-priorities),是给实施用的细致系分。
>
> 仿现有某份细致系分的结构骨架:参考分析→目标→数据设计→示例→实现流程。仿骨架不仿内容。

## 何时用 + 不该用

用:
- deep-read-by-boundary 已产精研结论(每块查到啥/透了/能给啥)
- 要写代码级系分给实施用

不该用:
- 还没精研(没精研结论硬写细致系分 = 编,必翻车,先去 deep-read-by-boundary)
- 只要浅显方案(那是 write-design-by-priorities)

## 硬依赖:必须接精研结论

本 skill **硬依赖** deep-read-by-boundary 的精研结论(每块:查到了啥/透了/能给系分啥)。

- **有精研结论**:接它,组代码级系分
- **没精研结论**:**不准写**——回去精研。没精研写细致系分等于编代码结构,实施时全是错的

## 结构:仿现有细致系分骨架(参考,不是固定)

样例粒度见 `reference/detailed-spec-structure.md`(已把领域概念抽象化,只示范骨架和代码级粒度,别照抄类型名/结构形态)。

一份现有细致系分长这样,可仿这套骨架:

1. **参考分析** —— 别人怎么做类似的事(对照可借的、避坑的)
2. **目标** —— 这次改造/新增在 runtime/编辑器/数据层要达到什么、产品目标
3. **数据设计** —— interface / 类型定义 / 数据结构。这块是细致系分的核心,要给到类型级
4. **示例** —— 典型配置/用法的完整示例(完整数据/代码),让人一眼看到产物长啥样
5. **实现/渲染流程** —— runtime 怎么按数据执行、各层怎么改、分几步。落点到流程

**这是某份的结构,不是所有细致系分必走**。换任务结构会变——但"有数据设计+示例+实现流程"这种代码级细致,是细致系分的共性。

## 内容写法(代码级但守纪律)

- **interface/类型/JSON 该写就写** —— 这是细致系分,不是浅显方案,代码级结构是它的本职
- **示例要完整** —— 完整 JSON/代码示例,让人看到产物长啥样,不是片段
- **实现流程要落点** —— runtime 按啥序执行、编辑器改哪,到步骤级
- **每节对应精研结论的某块** —— 结构按精研结论组织,不为凑"标准系分模板"写。精研结论没的块别硬写
- **不贴源码锚点** —— 写清"这块在 X 能力里"让实施者能找到,但不写"见 xxx.ts L120"(同 write-design-by-priorities)
- **不重做研究** —— 精研没透的块不写系分,标"这块还没透,先去精研"
- **文档标题用"块名:角色"短形,别塞副标题** —— 标题给人扫列表抓重点,不是塞结论或技术栈清单。形如 `路径文本:细致系分` / `MSDF:细致系分`——块名在前、`细致系分`角色在后,和同块浅显方案(`块名:方案`)成对、列表里一眼区分。不要把"(补instancing+烘焙+shader+触发门)"这类技术点清单塞标题(那是实现流程该讲的,塞标题扫不出重点、和正文重复)。括号修饰只在块名有歧义时用一次,不堆。和 write-design-by-priorities 同款纪律。

## 防过拟合

- **不套别份系分的具体内容** —— "仿结构"是仿骨架(参考分析→目标→数据设计→示例→实现流程),不是抄某份系分的具体数据结构/概念
- **不为凑模板写** —— 精研结论没的块别硬写,宁愿少节别凑
- **不把细致系分写成浅显方案** —— 浅显方案在 write-design-by-priorities,本 skill 到代码级
- **不贴源码锚点 / 不堆字段表** —— 哪怕代码级,源码位置和纯字段罗列还是垃圾,用类型定义+示例代替
- **风格要像人写,不 AI 腔** —— 见 `reference/writing-style.md`。判断直说、明示推测边界、状态化描述、落点给动作清单、反"因此/综上/建议"三段论。换主题仍适用,不是抄句式

## 判据

- [ ] 接了精研结论?没编?
- [ ] 到 interface/类型/JSON 级了?(代码级)
- [ ] 有完整示例?
- [ ] 有实现/渲染流程到步骤级?
- [ ] 每节对应精研结论某块?没为凑模板写?
- [ ] 没贴源码锚点?没堆纯字段表?
- [ ] 实施者照这能动手?

## 迭代回环(精细系分不只一轮,该回头再研就回头)

写细致系分时常常发现精研结论不够透——这是正常的,不是失败。该回头就回头:

- **写到某节发现这块字段/接口怎么定不清楚**(精研结论没给够)→ **停下,不编**,回去 deep-read-by-boundary 把那块再研一轮
- **写时发现某前提假设没验**(比如"以为 X 引擎支持 Y"但代码里没找到 Y)→ 回去 research/deep-read 重验那块
- **写时发现边界没定全**(漏了个硬骨头)→ 回去 define-research-boundary 补那块边界再研
- **不硬编**:某块系分不清楚凭什么写,标 TODO 跑路 = 埋雷。停下来回头研透,再回来写

判据:写每一节时能不能凭精研结论直接落代码级?落不了 = 精研没透那块,回去研。

## 一句话

> 精研透了写代码级细致系分:interface/JSON 设计+完整示例+实现流程,仿"参考→目标→数据→示例→实现流程"骨架。按精研结论组织不为凑模板,代码级但不贴源码锚点不堆字段表。没精研结论不准写。

# 细致系分结构参考(摘要,不是真实文档)

> 本文件示范"细致系分应该到什么粒度、按什么骨架组织"。
> **不是真实文档,领域概念已抽象化**,只为展示到此为止的代码级粒度,不为照抄任何具体概念。

## 骨架(5 段,顺序可调但常这样)

### 1. 参考分析
别人怎么做类似的事,提炼可借的、避坑的。不长篇,点到为止——可借的范式是什么、哪里要避坑。

### 2. 目标
目标层(runtime/编辑器/数据层各要达到什么)、产品目标(面向哪些用户、给到什么能力)。明确范围:本期做什么、不做什么。

### 3. 数据设计(细致系分的核心,要到类型级)
interface / 类型定义 / 数据结构 + 关键说明。

抽象示意(到这个粒度):
```typescript
interface FeatureConfig {
  items: FeatureItemConfig[];
}

type FeatureItemConfig =
  | BasicItemConfig      // 基础类型A/B/C
  | AttachmentItemConfig; // 附加类型

interface BasicItemConfig {
  type: 'basic-a' | 'basic-b';   // 类型标识
  params: {
    /* 该类型所需参数,具体到字段 */
  };
  attachments?: AttachmentItemConfig[];  // 挂在该项上的附加项
}
```

类型定义要给到字段级,但不堆源码位置。关键点要说明:这结构怎么用、为什么这么分(为什么 basic 和 attachment 分开等)。

### 4. 示例
典型配置/用法的完整示例(完整数据,不是片段),让人一眼看到产物长啥样:

```json
{
  "items": [
    { "type": "basic-a", "params": { /* ... */ }, "attachments": [ /* ... */ ] },
    { "type": "basic-b", "params": { /* ... */ } }
  ]
}
```

展示:典型场景的组合(主用法 + 叠加用法)。配几条说明:渲染/执行时按数组序逐项,前打底后叠加。

### 5. 实现/执行流程
runtime 怎么按数据执行,数步骤级:

1. 读入配置,解析成执行用数据(扁平化/校验/补默认)
2. 把每项转成执行器(工厂模式常见:按 type 映射到大致的 executor/drawer)
3. 按序执行每项:基础类型直接产出、附加类型只设状态等后续带出
4. 全部执行完产出最终结果

到"分几步、各步做什么"的粒度,不堆源码引用。

## 别照抄什么

- **类型名/字段名**:上面 basic-a/attachment 是抽象占位,不是真实概念。你的细致系分用自己领域的真实类型名
- **数据结构形态**:`items` 数组 + type 联合 + attachments 挂载,这个"列表+分类+附加"只是某种需求的结构,**不是所有细致系分都要这个形态**。换需求可能完全不同(树/图/单对象),按你的精研结论定
- **实现流程的"工厂/executor"模式**:也是某种实现选择,不是模板

## 只学什么

- **粒度**:数据设计到类型级(字段名)、示例完整、流程到步骤级
- **骨架**:参考分析→目标→数据设计→示例→实现流程,这个顺序大致通用(可调)
- **每节对应需求点**:不为凑模板写,数据设计里每个类型都应服务某个真实需求点

## 判据

- 你的细致系分到了 interface/类型级?示例完整?流程到步骤级?
- 但你写的类型名/结构形态是你的领域的,不是这份抽象示意的占位?
- 每个数据结构/流程步骤都有"为什么这么设计"在精研结论里撑着?

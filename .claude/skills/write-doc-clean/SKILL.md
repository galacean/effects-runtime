# Write Doc Clean

> 独立可用。给要点/结论,写出干净、不堆垃圾、人能看懂的文档。
> 与 write-design-by-priorities 区别:那个硬链接 research、写"拆解推理叙事";本 skill 不要求 research,按给的要点写,但同样守"不堆垃圾"。

## 一句话

> 给你要点,写出**不堆垃圾章节、按重点、人能看懂**的文档。不套通用模板填空,不写没人看的技术细节,每章都得"挣"它的位置。

## 何时用本 skill vs write-design-by-priorities

| 场景 | 用哪个 |
|---|---|
| 跑过 research-before-design,有"重要推理"(对的推理链+典型错误+决策资料) | **write-design-by-priorities**(硬链接 research,写"怎么拆出来的"叙事链) |
| 没跑 research / 小方案 / 人已想清楚直接给结论 | **本 skill write-doc-clean**(按要点写,守不堆垃圾) |

要写"这个需求怎么被拆解出来的、为什么这么推"——用前者;只要把已知要点写成干净文档——用本 skill。

## 四条铁律

### 1. 章节去留硬判据(最硬,治垃圾章节)

**每写一章,先过这关:删了这章,读者还能不能懂?能懂就删。**

- "概述""背景介绍""术语表"——删了不影响懂 → 删
- "概述"这种没信息量的通用标题,换成能传达信息的标题,或整章删
- 宁可少章节也别硬填。AI 写文档最容易犯的病:**为凑模板堆一堆删了也不影响懂的章节**

### 2. 按重点组织,不套模板

- 大章节对应**重点**(要传达的关键信息),不是对应"背景/目标/架构/计划"这种通用标题
- 重点详写,非重点略写(一两句或并进别处)——前提是过了铁律1
- 自检:把大标题遮住,还能不能看出文档要讲啥?看不出 = 又套模板了

### 3. 不写技术细节、不贴源码锚点

- ❌ 不写字段映射细节表(哪字段填哪字段)
- ❌ **不贴源码锚点**(文件:行号、"见 xxx.ts L120")——人不会去文档查源码位置,真查用 IDE/grep,文档写位置是负担
- ❌ 不写 API 签名、实现伪码

细节留实施时深挖,文档讲清"要干嘛、怎么做"就停。

### 4. 每节需求导向

每节开头问"这节对读者有啥用",答不上来就删或并。常见废话:
- 堆术语不解释、列背景不连重点、写实现不连用途
- 通用标签标题(Overview/Details)换成能传达信息的标题

## 读感约束(不写死步骤)

不给固定流程清单(那是 documentation 的病)。给 5 条**读感约束**——章节怎么排、留哪些,由约束推出来:

1. **从重点出发** —— 开头让读者看到文档要解决/传达什么,别绕背景
2. **依据先于结论** —— 支撑结论的依据在结论之前,读者才能信
3. **重点先于细节** —— 关键信息在前,细节/边角在后或省略
4. **相关内容聚合** —— 同一件事的各方面聚一处,别散
5. **可执行/可行动收尾** —— 文档最后落到"读完该干啥"(下一步/验收/待确认),别读完没着落

满足这 5 条,几步都行。**别凑步骤,凑约束**;每章还要过铁律1。

## 借来的纪律(从 obsidian-tech-doc)

- **章节要挣位置**:只加"挣得它在文档里位置"的章节,不是模板里有就填
- **一个章节一个观点**:别一节塞三件事;平行信息用表/列表,别散文堆
- **对判断要诚实**:说"X 不支持 Y"这种判断,已证还是推测要说清,别用确定性措辞填没把握的坑——但不贴源码位置(见铁律3)

## 防过拟合 + 防滥用

- ❌ 把"读感约束"当固定步骤清单凑章节 → 是"读者读着顺"的要求,不是"必写的章",别凑。每章得过铁律1
- ❌ 给一个"标准章节清单" → 本 skill **不给清单**,给"怎么决定章节"的原则
- ❌ 小到一句话能说清的事也走全套 → 直接说,别走过场
- ❌ 写着写着塞技术细节/源码锚点 → 回铁律3,删

## 案例(示意,非模板)

> 注:示意怎么"按要点写干净",非所有文档模板。

**给的要点**:某服务要做限流,阈值 1000 QPS,超了 429,用令牌桶。

**干净写法**(按重点,不堆垃圾):
- 限流目标:1000 QPS,超限返 429(为什么这个阈值:压测峰值)
- 实现:令牌桶(为什么不用计数器:令牌桶支持突发)
- 待确认:集群还是单机限流?(影响阈值算法)

**不要这么写**(堆垃圾):"概述/背景/术语表/限流原理介绍/令牌桶算法详解/参考资料"——删了概述/背景/术语表都不影响懂,属于垃圾章节。

## 一句话收尾

> 给要点,写干净文档。每章过"删了还懂不懂"判据,按重点组织,不写技术细节不贴源码。要写"怎么拆出来的"推理叙事,去用 write-design-by-priorities(它接 research)。
